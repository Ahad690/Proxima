## Summary

This commit moves the global lock file from within the project's `REVIEW_DIR` to `~/.proxima-review.lock` in the home directory (`cli/proxima-review.cjs:L26`), making it a machine-wide cross-project lock. It also replaces the old "skip-immediately-if-locked" behavior with a new `acquireLockWithRetry()` async polling loop (`cli/proxima-review.cjs:L67–L90`) that waits up to 60 minutes, polling every 10 seconds, before giving up. The stale-lock warning log line was removed silently. I did not need to look up external API docs for this change, as it is entirely self-contained Node.js `fs`, `os`, and async timer usage.

***

## What's Good

- **Atomic lock write is preserved** — `{ flag: 'wx' }` on `fs.writeFileSync` (`cli/proxima-review.cjs:L58`) is the correct pattern to prevent TOCTOU races on the creation side. This was good before and remains intact.
- **Silent unlink on `releaseLock`** — `try { fs.unlinkSync(LOCK_FILE); } catch {}` (`cli/proxima-review.cjs:L93`) is a clean, non-throwing release that avoids crashes if the file was already cleaned up.
- **Cross-project isolation is the right design call** — moving the lock to `os.homedir()` (`cli/proxima-review.cjs:L26`) is the correct architectural decision for preventing multiple repo hooks from hammering the same AI hub simultaneously. The code comment explains *why* clearly.
- **Repo identity added to lock metadata** — writing `repo: findGitRoot()` into the lock file (`cli/proxima-review.cjs:L60`) is a thoughtful observability improvement; it lets you inspect which project is holding the lock.
- **Graceful catch on stale unlink** — wrapping the stale-lock `unlinkSync` in a silent try/catch (`cli/proxima-review.cjs:L47`) is correct; a race between two processes discovering a stale lock simultaneously should not crash either one.
- **`firstWait` flag gives a clean "waiting..." vs "acquired" UX** — printing the wait message only once (`cli/proxima-review.cjs:L78–L82`) instead of on every poll is good terminal hygiene.

## Issues & Suggestions

- **`maxWaitMs` default of 60 minutes is unreasonably long for a CLI tool** (`cli/proxima-review.cjs:L68`). A git hook or CI runner will silently stall for an hour if anything goes wrong. This should be at most 10–15 minutes (or configurable via `PROXIMA_REVIEW_LOCK_TIMEOUT_MS`). Consider also printing a "still waiting... (Xm elapsed)" heartbeat every minute so the user knows the process hasn't frozen.

- **Stale lock warning log was silently removed** (`cli/proxima-review.cjs:L43`). The old line `console.log(yellow('⚠') + ' Stale lock found (from ' + lock.shortSha + '), clearing')` was deleted without replacement. If a stale lock is detected and cleared, users lose all visibility. This is an operational regression — restoring the warning (or replacing it with `log(...)` using the passed-in logger) is important for diagnosing stuck/crashed CI jobs.

- **`acquireLockWithRetry` logs via `log` but is called before `log` is defined in `runReview`** — if `log` itself depends on the review context (e.g., prefixes the SHA), the "Waiting in line" message at `cli/proxima-review.cjs:L79` may emit before the caller has set up its log context. Verify the `log` closure captures everything it needs before the `await acquireLockWithRetry(sha, log)` call at `cli/proxima-review.cjs:L244`.

- **`tryAcquireLock` no longer creates `REVIEW_DIR`** (`cli/proxima-review.cjs:L39`). The removed `if (!fs.existsSync(REVIEW_DIR)) fs.mkdirSync(REVIEW_DIR, { recursive: true })` guard was responsible for ensuring the output directory exists before writing. This responsibility now implicitly falls on something else. If `REVIEW_DIR` creation is not guaranteed elsewhere before first use, the rest of the program will crash when it tries to write a review file. This needs to be moved to an explicit initialization step in `runReview` or early in the program.

- **No polling progress message over time** (`cli/proxima-review.cjs:L83–L87`). After the initial "Waiting in line..." message, the process is silent for up to 60 minutes. Any developer watching the terminal will think the process is hung. Add a periodic log every ~60 seconds: e.g., `log(dim('   Still waiting... (' + Math.round((Date.now() - start) / 60000) + 'm elapsed)'))`.

- **`findGitRoot()` is called inside `JSON.stringify(...)` inside `tryAcquireLock`** (`cli/proxima-review.cjs:L60`). This is called in a tight retry loop (every 10 seconds). `findGitRoot()` almost certainly calls `execSync('git rev-parse --show-toplevel')` — spawning a subprocess on every failed lock attempt over 60 minutes is wasteful. Cache the value once at module load time or pass it in as a parameter.

- **No check that the waiting `commitSha` doesn't match the lock holder's SHA** (`cli/proxima-review.cjs:L68–L90`). If the same commit triggers two hook invocations simultaneously (e.g., a rebase loop or force-push race), both processes will wait for each other indefinitely until timeout. Adding a check like `if (lock.sha === commitSha) { throw new Error('Deadlock: same commit already holds the lock'); }` would short-circuit this.

## Security & Performance

- **Lock file in home directory is world-readable on shared machines** (`cli/proxima-review.cjs:L26`). `~/.proxima-review.lock` is created without explicit permissions. On multi-user machines or shared CI agents, other users could read the lock file and learn which git repo is currently being reviewed (via the `repo` field). Consider writing with `{ mode: 0o600 }` in `fs.writeFileSync` to restrict read access to the owner.

- **Polling every 10 seconds × 360 iterations = 3600 `fs.existsSync` + `JSON.parse` + `execSync` calls at worst** (`cli/proxima-review.cjs:L84`). This is negligible for a developer workstation but is meaningless overhead on a CI runner with a 10-minute timeout. Pair a lower default `maxWaitMs` with an exponential backoff (e.g., 10s → 20s → 30s, capped at 60s) to reduce syscall churn over long waits.

- **`JSON.parse(fs.readFileSync(...))` in `tryAcquireLock` has no size guard** (`cli/proxima-review.cjs:L43`). A maliciously crafted or corrupted lock file with a very large payload could cause memory issues. A simple `stat` size check before parsing (reject if > 1KB) would eliminate this theoretical risk.

***

## Overall Score: 7/10

The architectural intent is correct — a home-directory lock is the right solution for cross-project serialization. The new retry/queue behavior is a significant UX improvement over silently skipping. However, the 60-minute default timeout is dangerously long for a CLI tool, the silent removal of the stale-lock warning is an operational regression, the `REVIEW_DIR` initialization concern could cause a hard crash on first use, and the `findGitRoot()` call inside the polling hot path is a minor but unnecessary inefficiency.

***

## Recommendations

1. **Restore the stale-lock warning** at `cli/proxima-review.cjs:L43` — replace the removed `console.log` with `log(yellow('⚠') + ...)` using the passed-in logger for consistency.
2. **Reduce default `maxWaitMs` from 60 min to 10 min** at `cli/proxima-review.cjs:L68` and expose it as `PROXIMA_REVIEW_LOCK_TIMEOUT_MS` env var.
3. **Move `REVIEW_DIR` mkdir back** to `runReview()` initialization (or keep it in `tryAcquireLock` at `cli/proxima-review.cjs:L39`) — verify it isn't silently missing elsewhere.
4. **Add a per-minute heartbeat** inside the `while` loop in `acquireLockWithRetry` (`cli/proxima-review.cjs:L83`) so long waits are visible.
5. **Cache `findGitRoot()`** — hoist the call out of the `tryAcquireLock` inner logic and pass the result as a parameter to avoid repeated `execSync` calls during polling.
6. **Add same-SHA deadlock detection** — check `lock.sha === commitSha` early in `tryAcquireLock` and throw rather than wait.
7. **Write lock file with `mode: 0o600`** at `cli/proxima-review.cjs:L55–L60` on shared/CI machines to prevent information disclosure via the `repo` path in lock metadata.
