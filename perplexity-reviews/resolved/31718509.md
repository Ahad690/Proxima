## Summary

This commit adds Windows-specific spawn logic to `spawnBackground()` using `cmd.exe /c start "" /b` to suppress a new console window on detached Node.js processes, and hoists the `findGitRoot()` call into a shared variable to avoid calling it twice. The motivation is to fix a known Windows behavior: `windowsHide: true` is documented to be silently ignored by the OS when `detached: true` is also set for console-subsystem processes. The `cmd.exe start /b` approach is a recognized workaround. I verified the behavior of `start /b`, the `""` empty title quoting requirement, Node.js stdio redirection across a `cmd.exe` shell intermediary, and `process.execPath`/`__filename` path-with-spaces behavior on Windows against Node.js official docs and community references.

## What's Good

- **`findGitRoot()` deduplication** (`cli/proxima-review.cjs:L394-L395`). The prior code called `findGitRoot()` inline inside the `spawn` options object. Hoisting it into `const gitRoot` at the top of the function means a single call regardless of the `isWin` branch taken — clean and correct.
- **Accurate platform detection** (`cli/proxima-review.cjs:L394`). `process.platform === 'win32'` is the correct Node.js idiom for detecting Windows — it covers all modern Win32 builds including 64-bit Windows where `platform` is still `'win32'`.

The `""` prevents `process.execPath` from being swallowed as a title when it is quoted (which it may need to be on paths with spaces). This is a subtle but essential correctness detail, and getting it right is good.
- **Removed `windowsHide: true` from Unix path** (`cli/proxima-review.cjs:L425-L430`). Since `windowsHide` has no effect on non-Windows platforms per the Node.js docs, removing it from the Unix branch is a clean trim of dead options.
- **Non-Windows branch preserved cleanly** (`cli/proxima-review.cjs:L423-L430`). The original clean Unix spawn logic is reproduced faithfully with no unintended changes — a safe split.

## Issues & Suggestions

**[CRITICAL] `stdio` redirection is broken for the Windows `cmd.exe` path**
`cli/proxima-review.cjs:L416-L420`

When you spawn `cmd.exe` as the process, the `stdio` option in Node.js applies to the `cmd.exe` process itself — **not** to the child it launches via `start /b`. The inner Node.js process (`process.execPath`) is spawned by `cmd.exe` as a fully independent process with its own stdio handles, completely disconnected from the file descriptors `out` passed in `['ignore', out, out]`. As a result, the background review worker's stdout/stderr will **not** appear in `background.log` — they will be lost. This silently defeats the entire purpose of the log-file setup at `cli/proxima-review.cjs:L410-L412` for Windows users.

To actually redirect stdout/stderr into the log file via `cmd.exe start`, the redirection must be inside the `start` command's arguments using shell syntax:

```js
// Correct Windows approach: redirect via shell within the cmd invocation
const logFilePath = path.join(REVIEW_DIR, 'background.log');
child = spawn('cmd.exe', [
    '/c',
    `start "" /b ${process.execPath} ${__filename} ${sha} >>"${logFilePath}" 2>&1`
], {
    detached: true,
    stdio: 'ignore',
    cwd: gitRoot,
    env: cleanEnv,
    windowsHide: true
});
```

However, this introduces path-quoting complexity (see below). Alternatively, consider abandoning the `cmd.exe` wrapper and instead using `{windowsHide: true, detached: true, shell: false}` directly — which, per community testing, does suppress the window on most modern Windows 10/11 + Node versions even though the docs warn otherwise. Or, write the child's own output to the log from *within* the child process itself at startup.

**[CRITICAL] `process.execPath` and `__filename` are not quoted — will break on paths with spaces**
`cli/proxima-review.cjs:L415`

```js
['/c', 'start', '""', '/b', process.execPath, __filename, sha]
```

When Node.js calls `spawn('cmd.exe', args, ...)`, it joins these arguments into a command line string for the Windows process creation API. `process.execPath` on a typical Windows installation resolves to something like `C:\Program Files\nodejs\node.exe`, which contains a space. Without quoting, `cmd.exe` will interpret `Files\nodejs\node.exe` as a separate token and `start` will fail silently or launch the wrong executable. You must quote both:

```js
['/c', `start "" /b "${process.execPath}" "${__filename}" "${sha}"`]
// with shell: false (default) or using windowsVerbatimArguments: true
```

Or pass it as a single shell string with `{shell: true}`. Note that SHA values won't contain spaces, but the defensive quoting is still required for the paths.

***

**[MAJOR] `child.unref()` may not detach the grandchild correctly via `cmd.exe`**
`cli/proxima-review.cjs` (following `L432`, not shown in diff but affected)

`child.unref()` detaches the `cmd.exe` *wrapper* process from Node's event loop, but the actual background Node.js worker is a grandchild spawned by `cmd.exe`. Once `cmd.exe` finishes executing the `start /b` command, it exits — and whether the grandchild stays alive depends on whether Windows has properly detached it. With `start /b` and `detached: true` on `cmd.exe`, the grandchild *should* survive, but there is no deterministic guarantee that `child.unref()` on the intermediate `cmd.exe` process provides the same lifecycle semantics as calling it directly on the worker process. This should be stress-tested and documented with a comment.

***

**[MODERATE] `windowsHide: true` is still passed on the Windows branch but remains ineffective**
`cli/proxima-review.cjs:L421`

The comment at `L407-L410` explicitly explains that `windowsHide` is ignored when `detached: true` is used — that's the entire reason for the `cmd.exe` workaround. Yet `windowsHide: true` is still present in the Windows spawn options at `L421`. This is dead/contradictory code and will confuse future readers. It should be removed from the Windows branch.

***

**[MODERATE] The `cmd.exe`/`start` approach makes `cwd` semantically unreliable**
`cli/proxima-review.cjs:L419`

The `cwd` option passed to the outer `spawn` sets the working directory of `cmd.exe`, and `cmd.exe` will inherit that as the CWD for the `start /b` child. However, `start /b` can override this via its own working-directory semantics, and when paths are not quoted correctly (see CRITICAL above), `cmd.exe` may not launch the process from the intended `gitRoot`. If the `gitRoot` path itself contains spaces, this silently fails. The robustness of this entire approach depends on the quoting being correct end-to-end.

***

**[MINOR] No error event handler on `child` for the Windows branch**
`cli/proxima-review.cjs:L413-L422`

If `cmd.exe` itself fails to spawn (e.g., `PATH` manipulation in `cleanEnv` removes it, or the system is in a broken state), the `spawn` call will emit an `'error'` event that goes unhandled and crashes the parent process. The Unix branch has the same issue, but the Windows path is more fragile because it chains through a shell. A minimal defensive handler should be attached:

```js
child.on('error', (err) => {
    // Best-effort: log to stderr; parent should not crash on background spawn failure
    process.stderr.write(`[proxima] background spawn failed: ${err.message}\n`);
});
```

## Security & Performance

**Security:**
The `cleanEnv` construction (`cli/proxima-review.cjs:L397-L405`) strips all `GIT_*` variables, which is the correct approach to prevent environment injection from parent Git hooks into the child process. However, on the Windows `cmd.exe` path, the command line is assembled from `process.execPath`, `__filename`, and `sha` without sanitization. While `sha` is a Git SHA (hex-safe), if `process.execPath` or `__filename` contains characters with special meaning in `cmd.exe` (e.g., `&`, `|`, `^`, `%` via unusual install paths or enterprise environments), they could be interpreted as shell metacharacters by `cmd.exe`. Proper quoting with `"` around each path mitigates this but does not fully eliminate the risk if paths contain embedded double quotes .

**Performance:**
The `findGitRoot()` deduplication (`cli/proxima-review.cjs:L395`) is a small but correct optimization. No other performance concerns introduced by this diff.

## Overall Score: 5/10

The intent and diagnosis are exactly right — `windowsHide` really is unreliable on Windows with `detached: true`, and the `cmd.exe start /b` pattern is a legitimate workaround. The `findGitRoot()` deduplication is clean. However, the implementation has two critical correctness bugs: stdio redirection is silently broken for the Windows path (logs will be lost), and unquoted paths will cause silent failures for any user with spaces in their Node.js install path (essentially all Windows users who installed to `Program Files`). These are not edge cases — they are the norm on Windows.

## Recommendations

1. **(Highest Priority) Fix stdio redirection on the Windows branch** (`cli/proxima-review.cjs:L416-L420`). Either move the log-file redirection inside the shell command string (e.g., `>>"${logFile}" 2>&1` appended to the `start` invocation), or redesign the child process to open and write to `background.log` itself at startup. The current code silently discards all output on Windows.

2. **(Highest Priority) Quote `process.execPath` and `__filename` in the Windows args array** (`cli/proxima-review.cjs:L415`). Both must be wrapped in double quotes to handle spaces in paths like `C:\Program Files\nodejs\node.exe`. Consider using a single shell-string argument rather than an args array to have full control over quoting.

3. **(Medium Priority) Remove `windowsHide: true` from the Windows branch** (`cli/proxima-review.cjs:L421`). It is explicitly called out as ineffective in the comment above it, and leaving it in is misleading. Delete it from the Windows spawn options.

4. **(Medium Priority) Add a `child.on('error', ...)` handler** on both branches (Windows path most urgently). A silent spawn failure should not crash the parent process running inside a Git hook.

5. **(Low Priority) Add a code comment explaining the `child.unref()` lifecycle** for the Windows grandchild scenario — specifically that `cmd.exe` exits after launching the worker and the worker should survive independently, so future maintainers understand the expected process tree behavior.
