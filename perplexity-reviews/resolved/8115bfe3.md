## Summary

This commit does two things: it **moves the "review already exists" early-exit check to before `acquireLockWithRetry`**, and it **extends that check to also look for the file inside a `resolved/` subdirectory**. The motivation is sensible — avoid paying the cost of acquiring a distributed file lock only to immediately release it when the review was already generated. The logic is straightforward and the change is small, but the reordering introduces a subtle yet significant **TOCTOU (Time-of-Check-to-Time-of-Use) race condition** that wasn't present in the original design. No external schemas or APIs were verified via search for this review, but Node.js `fs.existsSync` TOCTOU behavior and file-locking best practices were confirmed against official recommendations.

***

## What's Good

- **`resolved/` subdirectory support is correct in intent** (`cli/proxima-review.cjs:L246`). Checking both `REVIEW_DIR/<sha>.md` and `REVIEW_DIR/resolved/<sha>.md` before doing any work means already-resolved reviews are properly skipped, preventing redundant API calls. This is a meaningful feature addition.
- **`mkdirSync` hoisted with the new early check** (`cli/proxima-review.cjs:L245`). Ensuring `REVIEW_DIR` exists before reading it is the right order of operations and avoids a potential crash if `REVIEW_DIR` doesn't yet exist at skip-check time.
- **Removed now-redundant `releaseLock()` call** (old code at `L265`). The original code called `releaseLock()` before returning inside the post-lock exists check. Moving the check pre-lock correctly eliminates that call, reducing the chance of a stale lock release.

- **Blank line left after lock acquisition** (`cli/proxima-review.cjs:L261`). The removed dead line (`const reviewFile = ...` was effectively orphaned) is cleaned up properly, keeping the post-lock block tidy.

## Issues & Suggestions

**[CRITICAL] TOCTOU Race Condition — Check Is Now Outside the Lock**
`cli/proxima-review.cjs:L244-L250`

The entire purpose of `acquireLockWithRetry` is to serialize access so that only one process at a time writes a review file. By moving the existence check *before* the lock is acquired, two concurrent processes can both pass the `if (exists)` check simultaneously (the file doesn't exist yet for either), both acquire the lock in sequence, and both end up writing (and potentially overwriting or duplicating) the review. The original code performed the check *inside* the critical section — which is the correct pattern. The performance win of skipping the lock is real, but it must be done safely:

```js
// SAFER pattern: fast pre-check (accept false negatives), then authoritative check inside lock
const likelySeen = fs.existsSync(path.join(REVIEW_DIR, shortSha + '.md')) ||
                   fs.existsSync(path.join(REVIEW_DIR, 'resolved', shortSha + '.md'));
if (likelySeen) {
    log(yellow('⏭') + '  Review already exists for ' + shortSha + ', skipping');
    return;
}

// Acquire lock, then do the authoritative check inside
await acquireLockWithRetry(sha, log);

// Authoritative check inside the critical section
const reviewFile = path.join(REVIEW_DIR, shortSha + '.md');
const resolvedFile = path.join(REVIEW_DIR, 'resolved', shortSha + '.md');
if (fs.existsSync(reviewFile) || fs.existsSync(resolvedFile)) {
    log(yellow('⏭') + '  Review already exists for ' + shortSha + ', skipping (post-lock)');
    releaseLock();
    return;
}
```

This is a double-checked locking pattern: the pre-lock check is a cheap optimization for the common case (review exists), while the post-lock check is the safety net for the rare concurrent-write case.

***

**[MAJOR] `releaseLock()` Is Never Called on the "already exists" Post-Lock Path**
`cli/proxima-review.cjs:L260` (context)

The original code explicitly called `releaseLock()` before `return` when the file already existed inside the lock. That call was correctly deleted — but *only* because the check was moved outside the lock. If you apply the fix above (double-checked pattern), the inner `releaseLock()` call must be restored for that early return path, or the lock will remain held indefinitely and all future processes for this SHA will hang.

***

**[MODERATE] `resolved/` directory existence is never ensured before the `existsSync` call**
`cli/proxima-review.cjs:L247`

`fs.existsSync(path.join(REVIEW_DIR, 'resolved', shortSha + '.md'))` will return `false` (correctly) if `resolved/` doesn't yet exist — but this is implicitly relying on `existsSync` gracefully returning `false` for paths whose parent directories don't exist. That behavior is correct in Node.js today, but it is not documented as a guarantee and is subtly fragile. Consider a simple guard or restructuring to `fs.existsSync(path.join(REVIEW_DIR, 'resolved'))` separately if you ever need to enumerate that directory.

***

**[MINOR] `mkdirSync` is now called unconditionally on every `runReview` invocation, even for commits that will be skipped**
`cli/proxima-review.cjs:L245`

Previously, `mkdirSync` was called only after the lock was acquired (i.e., the process was committed to doing real work). Now it runs before the skip check, meaning every invocation — including ones that immediately return due to an existing review — pays a filesystem syscall. In high-frequency batch runs (e.g., reviewing hundreds of commits in a loop), this is unnecessary overhead. Move `mkdirSync` to after the early skip check, or lazy-init it only when you're about to write:

```js
// Move this to just before writing the review file, not before the skip check
// fs.mkdirSync(REVIEW_DIR, { recursive: true }); // only needed right before write
```

Or at minimum restructure so the guard is: `if (!fs.existsSync(REVIEW_DIR))` is kept inside the `exists` block as the path-building requires it anyway.

***

**[MINOR] The `exists` variable name is too generic for its context**
`cli/proxima-review.cjs:L246`

`exists` is ambiguous. In a larger function, a reader has to look up what it refers to. Prefer `reviewAlreadyExists` or `reviewFileExists` to make the intent immediately clear at the `if (exists)` call site on `L249`.

***

**[MINOR] No check that `resolved/` is a directory vs. a file**
`cli/proxima-review.cjs:L247`

If `REVIEW_DIR/resolved` were accidentally a file rather than a directory (e.g., from a bad migration), `path.join(REVIEW_DIR, 'resolved', shortSha + '.md')` would return `false` from `existsSync` silently, causing previously-resolved reviews to be re-processed. A defensive `fs.statSync` or `fs.lstatSync` check to assert it is a directory could prevent silent data loss.

## Security & Performance

**Security:**
The TOCTOU race condition described above (`cli/proxima-review.cjs:L244-L250`) is not just a correctness issue — in a shared CI environment where multiple agents run `proxima-review` in parallel against the same `REVIEW_DIR` (e.g., a mounted network volume), this creates a window where two agents can both believe no review exists and both write, potentially overwriting a completed review with a new one or causing duplicate billing for an AI API call. The fix is the double-checked locking pattern described above.

**Performance:**
The *intent* of this optimization — skipping lock acquisition for already-reviewed commits — is sound and meaningful. Lock acquisition with retry is likely the most expensive operation in this path (involves I/O, possible sleeps). The pre-lock check for the common case (`review exists → return immediately`) is a real win. However, the `mkdirSync` call at `cli/proxima-review.cjs:L245` before the check adds a redundant syscall on every invocation. Fix ordering so `mkdirSync` is deferred to the write path only.

The feature addition (supporting `resolved/`) is well-reasoned and the optimization intent (pre-lock skip) is sound, but the implementation introduces a TOCTOU race condition by removing the authoritative post-lock duplicate-check without replacing it with a safe double-checked locking pattern. This is a correctness bug in concurrent environments, which is the primary use case for a locking mechanism. The surrounding code quality is clean and readable.

## Recommendations

1. **(Highest Priority) Restore the post-lock existence check** at `cli/proxima-review.cjs:L260`. Apply the double-checked locking pattern — keep the new pre-lock check as a fast-path optimization, but re-add the `existsSync` check (now also covering `resolved/`) inside the critical section, with a `releaseLock()` before returning.

5. **(Low Priority) Optionally add a guard** verifying `REVIEW_DIR/resolved` is a directory (not a file) before building paths against it, to prevent silent misses on malformed directory state.
