# Code Review: a0796528

> feat: implement hardened local automation workflow with iterative reviews and safety checks

## Verdict


**FAIL** — the diff adds an automation loop, but the safety model is mostly documentary/config-only and several paths can apply, commit, or expose unintended changes.


## Implementation vs Intent Gap


- The workflow claims safety through config switches, but `allowGeneratedScripts`, `allowWorkflowModification`, and `allowReviewHistoryModification` from `proxima-automation.config.json:L16-L18` are not actually consulted by `scripts/lib/safety.cjs:L4-L94` or `scripts/proxima-loop.cjs:L161-L164`.
- The loop applies and commits `git add .` at `scripts/lib/git-utils.cjs:L76-L80`, so it can commit more than the generated patch, including untracked local files created during tests or repair.
- The “review history modification” guard is contradicted by the commit itself: dozens of files under `perplexity-reviews/` are added, while `scripts/lib/safety.cjs:L50-L52` only blocks `.github/workflows/`, not review archives.
- The local repair script has a path bug: `scripts/proxima-repair.cjs:L20` joins `config.gitRoot` with `config.reviewDir` even though `loadConfig()` makes `reviewDir` absolute at `scripts/lib/config.cjs:L68-L70`. With the default `/root/review`, the manual repair command searches the wrong place.
- The Proxima client timeout is weaker than it looks: `scripts/lib/proxima-client.cjs:L22` sets `timeout: 300000`, but Node documents that setting timeout does not abort by itself; it only emits a timeout event, so manual destruction is needed and must be correctly handled. This code does destroy on timeout at `L52-L55`, but the comment/option alone is not the real guarantee. [Node.js](https://nodejs.org/api/http.html?utm_source=chatgpt.com)
- The patch validation is superficial. `scripts/lib/safety.cjs:L4-L19` only checks for diff markers and markdown fences; `git apply --check` is the real syntactic gate later at `scripts/proxima-loop.cjs:L194-L201`.

- `scripts/proxima-loop.cjs:L246-L250` should persist rejected model output and validation reason under `repair/` for auditability.

- `scripts/lib/review-parser.cjs:L3-L35` needs tests for malformed reviews, emoji-only severity, lowercase headings, decimal scores, and missing sections. The added tests at `scripts/tests/automation-tests.cjs:L10-L29` cover only the happy path.
- `scripts/tests/automation-tests.cjs` is not wired into `package.json`; there is no `npm run` script to execute it.
- `docs/local-automation.md:L18-L19` describes patch validation and iterative repair, but does not document the `git add .` behavior or the risk of committing generated/untracked files.

## Security & Data Integrity


- **Worst-case repo corruption:** An AI-generated patch passes the shallow validators, tests generate files, and `git add .` at `scripts/lib/git-utils.cjs:L76-L80` commits unrelated secrets, logs, build artifacts, or the user’s pre-existing dirty work.
- **Policy bypass:** The config says workflow and review-history changes are disallowed (`proxima-automation.config.json:L16-L18`), but the validator only blocks `.github/workflows/` at `scripts/lib/safety.cjs:L50-L52`. A patch can modify `package.json` scripts, `.husky/`, `cli/`, review archives, or local automation code.
- **Prompt-to-patch supply chain risk:** The repair prompt at `scripts/proxima-loop.cjs:L143-L158` includes both review text and original diff. If the reviewed diff contains adversarial text telling the repair model to ignore rules, the only hard guard is weak regex/path validation.
- **Credential/file disclosure:** PR body generation includes `sessionDir` at `scripts/proxima-loop.cjs:L280-L282`; on real machines this can reveal usernames, repo layout, or `/root` deployment assumptions.
- **False clean state:** A malformed or nonconforming review causes `parseSeverityCounts()` to return zero at `scripts/lib/review-parser.cjs:L3-L11`; with passing tests, the loop exits clean even if the review contained serious findings outside the expected table.
