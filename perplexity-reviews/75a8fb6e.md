# Code Review: 75a8fb6e

> Add tip message about background review duration

## Summary

This is a single-line cosmetic commit adding a user-facing tip message (`proxima-review.cjs:L371`) immediately after the background spawn confirmation log. The message informs the developer that the background review may take 1–2 minutes to complete. No logic, configuration, or control flow is modified. No external API schemas or library patterns required research for this diff — this is purely a UX/messaging change.

***

## What's Good

- **`proxima-review.cjs:L371` — Message placement is correct.** The tip fires after `child.unref()`, meaning the background process is already detached before the message prints. There's no race condition or ordering issue.
- **`proxima-review.cjs:L371` — Consistent styling.** Using `cyan('💡')` matches the established visual language of the surrounding log lines (e.g., `cyan('🤖')` on `L370`), keeping the terminal output cohesive.
- **`proxima-review.cjs:L371` — Genuinely useful UX.** Without this message, a developer might assume the review is instant or already done. Setting the 1–2 minute expectation prevents confusion and premature `cat` of the review file.

***

## Issues & Suggestions

- **`proxima-review.cjs:L371` — Hardcoded time estimate will silently become wrong.** The string `'1-2 minutes'` is a magic literal with no relationship to actual timeout values, model latency, or configurable constants in the codebase. If the underlying API timeout or model changes, this message will mislead developers. The estimate should either be derived from a constant or kept intentionally vague:

  ```js
  // Option A — tie to a real constant if one exists
  console.log(cyan('💡') + ` Background reviews may take up to ${Math.ceil(REVIEW_TIMEOUT_MS / 60000)} minute(s).`);

  // Option B — vague but always accurate
  console.log(cyan('💡') + ' Background review is running — check .proxima/reviews/ when your push completes.');
  ```

- **`proxima-review.cjs:L371` — Message is not written to the background log.** Every other log line in `spawnBackground` uses `console.log`, which is correct for the parent process. However, the background child will never see this message, so it will not appear in `background.log`. This is consistent with the current design, but it means a developer tailing the log file gets no equivalent timing hint. Consider adding a matching entry in `logToFile` at the top of `runReview` (`proxima-review.cjs` around `L189`) when `isBg === true`:

  ```js
  if (isBg) logToFile('Review started — estimated completion: 1-2 minutes');
  ```

- **`proxima-review.cjs:L370-L371` — Two `console.log` calls could be one.** The queued message (`L370`) and the tip (`L371`) are always printed together. Combining them reduces clutter and makes the output a single, readable status line:

  ```js
  console.log(
      cyan('🤖') + ' Review queued for ' + yellow(sha.substring(0, 8)) +
      ' (background) — ' + cyan('💡') + ' may take 1-2 min.'
  );
  ```

  This is a minor style preference, not a bug — leave separate if the project convention favors one-message-per-`console.log`.

***

- **No performance implications.** A single synchronous `console.log` in the already-synchronous post-spawn block has negligible cost.

2. **(Low — `proxima-review.cjs` ~L189)** Add a mirrored `logToFile('Review started...')` entry at the top of `runReview` when `isBg === true`, so developers tailing `background.log` also get a timing expectation.
3. **(Optional — `proxima-review.cjs:L370-L371`)** Consider merging the two consecutive `console.log` calls into one line if the project style guide prefers concise terminal output.
