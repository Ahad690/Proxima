## Issues & Suggestions

**🟢 Minor**

- **The time estimate at `cli/proxima-review.cjs:L372` is hardcoded as a string literal `'1-2 minutes'`.** If the actual duration changes (e.g., due to a different model, a timeout adjustment, or infrastructure changes), this string will go stale silently. There is no single source of truth for the timeout value in this codebase that this message could reference. This is acceptable for now, but if a `REVIEW_TIMEOUT_MS` or similar constant is ever introduced elsewhere in `proxima-review.cjs`, the string here should be derived from it:
  ```js
  // If a constant exists, e.g.:
  const REVIEW_TIMEOUT_MINUTES = 2;
  console.log(cyan('💡') + ` Background reviews may take up to ${REVIEW_TIMEOUT_MINUTES} minutes to complete.`);
  ```
  For the current one-liner addition, this is not blocking — just worth keeping in mind as the codebase matures.

- **The message at `cli/proxima-review.cjs:L372` has no corresponding log in the background process itself** (e.g., a timestamp when the review actually completes or fails). A user waiting 1–2 minutes has no way to know if the process finished successfully, timed out, or crashed silently — they must check the output file manually. The tip raises the expectation; a completion signal would close the loop. This is a broader UX gap, not introduced by this commit, but this line makes it more noticeable.
