# Code Review: f43f6a6c

> refactor: remove redundant prompt size bounding (2MB limit exists in Proxima)

## Verdict
**FAIL** — the code does not safely remove prompt size bounding; it introduces a regression that can break processing for large diffs or reviews.

## Implementation vs Intent Gap
- The commit claims to remove "redundant prompt size bounding" because a 2MB limit exists in Proxima. However:
  - Line 197-204 removed the explicit truncation of `reviewContent` (`MAX_REVIEW_CHARS`) and the check on `rawDiff` (`MAX_DIFF_CHARS`).
  - There is now **no safeguard** against `reviewContent` exceeding any reasonable size. If `reviewContent` or `rawDiff` is larger than what downstream services (e.g., Proxima) can handle, this can fail silently or cause runtime errors.
  - The code assumes that Proxima's 2MB limit is sufficient without considering that `rawDiff` is concatenated with `reviewContent` and additional prompt text. The combined size could exceed Proxima's limit even if individually under 2MB.

| File:Line | Severity | Finding | Evidence |
|-----------|----------|---------|----------|
| scripts/proxima-loop.cjs:198-204 | 🔴 Critical | Unbounded `reviewContent` may exceed API limits | `boundedReview` truncation removed; large reviews can break prompt submission. |
| scripts/proxima-loop.cjs:207-212 | 🔴 Critical | Unbounded `rawDiff` may exceed API limits | Previous `MAX_DIFF_CHARS` check is gone; large diffs no longer prevented, risking failure of `git apply` patch generation. |
| scripts/proxima-loop.cjs:215 | 🔴 High | Concatenation of large strings without size check | `prompt` now embeds `${reviewContent}` and `${rawDiff}` directly, potentially exceeding Proxima’s 2MB or causing memory spikes. |
| scripts/proxima-loop.cjs:193 | 🟠 Medium | Directory creation race | `fs.existsSync` + `fs.mkdirSync` is not atomic; concurrent runs could throw `EEXIST`. |

## Missing Changes
- Related functions handling automated patch generation (`git apply`) or other `repair` pipelines should have been updated to either:
  - Respect the 2MB combined limit for prompt + diff, or
  - Implement streaming or chunked processing.  
  - Lines referencing `updateStatus({ status: "repair-context-too-large", ... })` were removed but no alternative mechanism added.
- Other prompt creation paths (if any) that previously used `MAX_REVIEW_CHARS` or `MAX_DIFF_CHARS` were not audited or adjusted. Potential inconsistencies remain.

## Security & Data Integrity
- **Worst-case scenario:** Sending an unbounded `reviewContent` or `rawDiff` could crash the Proxima service or the local process, causing:
  - Loss of intermediate code review or repair data.
  - Corruption of generated patches if the service truncates internally.
  - Memory exhaustion (OOM) on the server, which could be exploited by submitting extremely large diffs or reviews (DoS attack vector).
  - Inconsistent or partially applied patches leading to codebase corruption if `git apply` is used on incomplete output.

## Score: 2/10
- Only positive: removal of redundant truncation is conceptually acceptable if Proxima enforces limits.  
- However, the implementation fails to account for **combined prompt + diff size** and loses all safeguards (lines 197-212). This is a **critical regression**, not a harmless refactor.  

This change would be dangerous in production, especially for large repositories or long reviews.
